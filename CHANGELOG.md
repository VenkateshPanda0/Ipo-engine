# Changelog

All notable changes to IPO Engine are recorded here, in the
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/) format. The package version follows
[Semantic Versioning](https://semver.org/); the other version numbers (API, ruleset, analysis) are
independent and explained in `docs/VERSIONING.md`. The reasoning behind each change is in
`docs/decisions.md` (the D-numbers).

The screening app's history before it joined this package (to 2.0.1) is in
[`docs/screening/CHANGELOG.md`](docs/screening/CHANGELOG.md), linked below under "Earlier history".

## [Unreleased]

### Added

- Oversized request bodies are refused before they are read (`MAX_JSON_BODY_MB`, default 2): a POST, PUT or PATCH whose declared length, or whose chunked body so far, passes the limit gets 413 `PAYLOAD_TOO_LARGE` at once, with the usual request id, security headers and `no-store`; multipart uploads keep their own streaming limit. Before, a JSON body was read whole and then parsed: a 30 MB body took 446 ms and 127 MB of extra memory to be answered with a 422; now it is answered with a 413 in 28 ms, and a client sending gigabytes cannot make the server hold them. 8 tests (6 fail without the change).
- No API response can be kept by a shared cache: every response (the lists of people, tokens and notifications, both exports, the CSRF token, errors and unknown paths) now carries `Cache-Control: no-store` unless a route sets its own (the share page already did). Before, 33 of 33 readable routes sent no caching header at all, so a browser or an intermediary could keep, for example, the member list or an organisation export. A test walks every readable route from the API schema; it fails without the change.
- Dialog keyboard behaviour fixed and tested: the shared `Modal` re-ran its focus effect whenever its page re-rendered (pages pass a fresh `onClose` each time), so typing in a field inside a dialog could lose focus to the dialog on every keystroke and the opener was forgotten, and Tab could leave the dialog for the page behind it although it is marked modal. Now the effect runs once, focus is trapped (Tab wraps at both ends, stray focus is pulled back in), Escape closes exactly once, and focus returns to the control that opened it. 7 new unit tests; 3 of them failed before the fix (caret kept while the page re-renders, Tab wraps, stray focus pulled back), all 7 pass after; frontend tests 42 to 49.
- Accessibility, measured: an axe-core audit (WCAG 2 A and AA) of all 14 signed-in pages in both the light and the dark theme, and of the sign-in and invitation pages (`frontend/tests/e2e/a11y.spec.ts`, run in CI in the accounts-mode browser pass). Before: 6 of the 14 pages failed in the light theme (16 elements: secondary text `#6b7685` was 4.2:1 on the page background, 4.5:1 is required) and 9 of 14 in the dark theme, where every primary button was white on light blue at 2.4:1 because a more specific rule overrode the dark-theme text colour. After: 0 violations on all 31 page-and-theme combinations. Secondary text is now `#5f6978` (4.7:1 or better on every surface) and the dark-theme primary button uses dark text (8:1). Automated rules cover roughly a third of WCAG: keyboard and screen-reader review by a person is still to do (docs/roadmap.md).
- Sign-in hardening: the ID token's RS256 signature is now verified against the provider's published keys (`jwks_uri`), on top of the TLS channel the first version relied on. Only RS256 is accepted (not `none`, not an HMAC keyed with the public key), the key is picked by `kid`, key refetches are limited to one a minute so forged key ids cannot make the server hammer the provider, and a provider with no keys is refused unless `OIDC_VERIFY_SIGNATURE=false`. `cryptography` is now a declared dependency (it was already installed for the PDF stack). The test identity provider now signs with a real RSA key; 14 new tests cover tampered claims, a foreign key, `none`, HS256, ES256, RS512, key confusion, stripped signatures, rotation and the refetch limit, and the sign-in flow end to end. This removes the main caveat recorded in D-068.
- Webhook events can no longer be lost: they are queued by the same database transaction as the change they announce (through the audit record), instead of by the request handler afterwards. Before, a crash or error between "the change committed" and "the event was queued" dropped the event silently; now a change and its event exist together or not at all, a rolled-back change leaves no event, and a fault in the outbox itself is logged and never undoes the change. The same six events, payloads and signatures; 4 new tests (transactional commit, rollback, an outbox fault, a sign-off event reaching only its own organisation), on SQLite and PostgreSQL.
- Faster requests, same behaviour: the three per-request middleware layers (request id and log line, security headers, v0 deprecation) are now one layer, and a token or session is checked with one database query instead of four. Measured in process on one development machine (median of seven runs of 400 requests): health 2.1 to 1.5 ms, `/me` 3.9 to 3.0 ms, case list 5.1 to 4.1 ms per request; `tools/loadtest.py --selfhost` with 12 clients went from 72 to 84 requests per second, still 0 leaks and 0 unexpected responses. No header, status or error body changed (the existing middleware, security-header and deprecation tests pass unmodified).
- Operations: S3-compatible document storage (`STORAGE_BACKEND=s3`; a SigV4 signer checked against AWS's published test vector, no cloud SDK), optional invitation e-mail over SMTP (a header with a line break is refused, a failed send never loses the invitation), secrets from files (`DATABASE_URL_FILE`, `GOOGLE_CLIENT_SECRET_FILE`, `WEBHOOK_SIGNING_KEY_FILE`, ... ; a value set directly wins, an unreadable file stops the start), queue, webhook, organisation and session gauges on `/metrics`, a deployment layout (`deploy/compose.accounts.yaml`: PostgreSQL, API, workers, web; read-only containers, secrets as files) with Prometheus alert rules, `ipo accounts usage`, and `docs/OPERATIONS.md`. Tests keep the deployment files in step with the code: every setting the compose file sets is a real setting, every metric an alert uses is exposed, and `docker compose config` accepts it. A token's `last_used_at` is written at most once a minute instead of on every request.
- Intensive tests: thread races (parallel comments lose nothing; once a member is removed no later request with their token succeeds; two organisations hammering at once never see each other), properties over arbitrary input (spreadsheet cells never start with an executable character; any text makes a valid workbook; a return address never leaves the site; no non-public IPv4 or IPv6 literal is accepted as a webhook target; a signature verifies only for the exact body, secret and time), a 200-call random isolation fuzz across two organisations, and `tools/loadtest.py`, a load tool that checks for leaks as it measures (`--selfhost` starts a throwaway three-organisation server).
- The web app for accounts mode: a sign-in page (Google when the server has it, or a pasted API token), invitation pages, a team page (roles, invite links shown once, withdraw, remove), "my account" (personal tokens, browser sessions with sign-out-everywhere-else, download my data), an organisation page for admins (rename, four-eyes and webhook switches, webhooks with a one-time signing secret, usage, export, delete), notifications with an unread count, an organisation switcher, assignment and comments on every case (with an erase-with-typed-name control for admins), saved searches, "assigned to me" and CSV or Excel download on the case list, read-only share links on reports, a getting-started checklist on the dashboard. Cookie sessions send the CSRF token on every change (fetched once, refreshed once after a 403); tokens send none. Nothing appears when the server has accounts off. 11 unit tests and a Playwright pass in a real browser against an accounts-mode API (new CI steps); the existing browser workflow still passes against the unchanged local mode.
- Webhooks (`WEBHOOK_SIGNING_KEY` turns them on): an organisation admin registers up to 10 https endpoints and the events they receive (`case.created`, `document.processed`, `screening.completed`, `review.signed_off`, `comment.added`, plus a test `ping`). Deliveries are signed (`X-IPO-Signature: t=…,v1=HMAC-SHA256`, secrets derived from the server key so none is stored, rotatable), carry identifiers and names only, go through an outbox with backoff (1 min to 12 h) and are given up after `WEBHOOK_MAX_ATTEMPTS`, telling the admins. Targets are protected against server-side request forgery: https only, every resolved address must be public (loopback, private, link-local, carrier-grade NAT and metadata addresses are refused, a name with one private answer among public ones is refused), the connection is pinned to the validated address, redirects are not followed. A bug found by the tests, not by a user: an enum in a payload made the event vanish silently; payloads are now coerced to plain JSON. 32 tests on SQLite and PostgreSQL, including a real delivery to a local receiver.
- Spreadsheet exports and share links: `GET /api/v1/exports/cases|reports?format=csv|xlsx` (what the caller can see, the list filters honoured; a hand-written XLSX writer with no dependency; cells that start with `=`, `+`, `-`, `@`, tab or CR are turned into text so a company name cannot run as a formula) and read-only share links for one report (`POST /reports/{id}/shares`, 1 to 90 days, up to 20 live per report; the token is shown once and stored as a hash; revocable; views counted; unknown, expired and revoked links answer identically; the public route is rate-limited and served with the report CSP, `no-store` and `noindex`). Migration 0006; 19 tests on SQLite and PostgreSQL.
- Working together (accounts mode): assign a case to a member (`PUT /api/v1/cases/{id}/assignee`, `GET /cases?assignee=me`, "assigned to me" on the dashboard), comments on cases (viewers read, analysts write, authors and admins delete), in-app notifications for assignments and comments, per-person saved searches, organisation settings (`four_eyes`: the person who ran a screening cannot also sign it off, 409), a getting-started checklist (`/api/v1/onboarding`) and per-organisation usage counts (`/api/v1/org/usage`). Comments are included in the organisation export and in case erasure, and the tenant-isolation walker covers the new comment routes. Migration 0005; 17 new tests, run on SQLite and PostgreSQL.
- Data lifecycle: an organisation admin can export everything the organisation holds as a zip of JSON files (`GET /api/v1/org/export`, PDFs optional) and any person can export what is held about them (`GET /api/v1/me/export`, no secrets); an admin can erase a case for good (`DELETE /api/v1/cases/{id}?confirm=<exact name>`: rows, history and the stored PDF, which is kept if another case holds the identical file); an owner can switch an organisation off (sign-in, tokens and sessions stop at once) and `ipo accounts purge-org` erases it after the grace period. Erasure lifts the append-only triggers inside one transaction and restores them before commit (tested: they are back after success and after failure, on SQLite and PostgreSQL); the audit trail keeps an identifier-only record that the erasure happened. `ipo backup create|verify|restore`: a consistent online SQLite copy (or `pg_dump`), every stored PDF and a checksummed manifest; a damaged or incomplete backup is detected, and restore refuses to overwrite without `--force`. Round trips tested with data and documents on SQLite and PostgreSQL.
- Shared job queue and rate limits: `JOB_MODE=queue` leaves uploaded documents waiting in the database; any number of processes (the API itself, or `ipo worker`) claim them with one conditional update, so no job is taken twice (tested with four racing workers on SQLite and PostgreSQL), renew a lease while they work, and a job whose worker died is handed back after `JOB_LEASE_SECONDS`, or failed after `JOB_MAX_ATTEMPTS` so a poison document cannot loop. Starting a second process no longer marks another process's running jobs as failed (that restart behaviour is unchanged in the default `local` mode). `RATE_LIMIT_STORE=database` makes the upload limit one limit across processes, and `API_RATE_LIMIT_PER_MINUTE` adds a per-user request limit (429 with `Retry-After`). Migration 0004.
- PostgreSQL support (`DATABASE_URL=postgresql://…`, optional extra `postgres`, included in the container image): connection pool with liveness checks, URL normalised to the psycopg 3 driver, and append-only audit tables enforced by triggers on PostgreSQL as on SQLite (migration 0003). The whole application test suite (533 tests) passes unchanged against PostgreSQL 16 (`IPO_TEST_PG_ADMIN_URL=… pytest tests/screening` gives each app a fresh database), and a new CI job `postgres 16` runs it on every push. New tests assert the audit tables reject UPDATE and DELETE and that migrations round-trip on both backends.
- Accounts, part 2: browser sessions and optional Google sign-in (`GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`, off by default; authorization code with PKCE, single-use state bound to the browser, nonce and claim checks, no new dependency). Sessions are HttpOnly SameSite=Lax cookies (Secure in production or behind `TRUST_HTTPS`), stored only as a hash, with an absolute lifetime and an idle limit; every cookie-authenticated change needs the session's CSRF token and a known origin; sessions can be listed, revoked one by one or all but the current, and end at once when the user is suspended or removed. Invitations by link (shown once, expiring, revocable, bound to the invited address), invite-only sign-up by default (`SIGNUP_MODE=open` to change), an optional e-mail-domain allow list, per-session organisation switching. Tested end to end against an in-process identity provider (PKCE, nonce, replayed or foreign callbacks, forged claims, open redirects). The network code is confined to `screening/network/`, lazily imported and absent from a default start (D-068); `tests/test_offline.py` exempts only that package and `urllib.parse`.
- Accounts, part 1 (off by default, `ACCOUNTS_ENABLED=true`): organisations, users, memberships with per-organisation roles, and personal API tokens (`ipo_…`, shown once, only a SHA-256 stored, expiry, revocation, never above the owner's current role).
